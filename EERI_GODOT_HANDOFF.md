# Eeri — Godot implementation handoff

Status: **skeleton only** — the project boots, renders, and reads the real
asset manifest. No gameplay is ported.

Baseline commit: `314dd1f7058a8116ce3a63f819e5fce877592ba0` (the last Eeri
commit inside the Suds-Jack monorepo, `v15.37`, before the split)
Target: Godot 4.7.2 (this repo was built and gated against it; the project
file declares `4.3` features and should open on anything ≥ that)

This file is the coordination surface for whoever picks up the Godot port
next. It creates no new canon. Where it conflicts with the authority stack
below, the authority stack wins — same rule Piritori's equivalent handoff
uses, and for the same reason: a porting doc that starts inventing design is
how a fork starts.

## 1. Read before building, in order

1. `PHASING.md` — **newest owner direction, supersedes the rest where they
   disagree.** The 80/20 reference ratio (Crafted World 80 / Tropical Freeze
   20), the tool-reality table, and the phase gates.
2. `DESIGN.md` — what the game does. §4 is the level shape and the locked
   counts (12 levels, four worlds of three, `EERI 1-1` addressing). §6 is the
   asset queue. §8 is the ordered plan.
3. `ART_BRIEF.md` — the look.
4. `ART_PIPELINE.md` + `ART_TARGET.md` — how an asset is made and the quality
   bar it is made to. **Vendored copies** — see the note at the top of each;
   the canonical originals are shared with Kindling and live at the root of
   the old Suds-Jack monorepo.
5. `assets/README.md` + `assets/manifest.json` — the seam: node/clip
   contracts, layer rects, PNG/WEBP sizes.
6. `VERSIONS.md` — what shipped, and more usefully, the traps. 37 versions of
   them.
7. this handoff.

## 2. What already exists here (`godot/`)

```
godot/
  project.godot
  autoload/
    asset_registry.gd   parses data/manifest.json, reports live vs placeholder
    game_state.gd        empty placeholder for the one future run-state model
  scenes/
    main.tscn / .gd      proves the above two: prints a manifest summary on screen
  tools/
    sync-data.mjs         copies ../assets/manifest.json + every "live" file into data/
  tests/
    test_boot.tscn / .gd  the one gate: 8 checks, headless
  data/                   git-ignored — regenerated by sync-data.mjs
```

Run `node tools/sync-data.mjs` from inside `godot/` after every clone and
after every manifest change upstream (`--check` to gate instead of copy —
same two-mode shape as Piritori's script, and for the same reason: `data/`
must never become a second hand-kept copy of canon).

**This is further along than "empty skeleton" sounds.** 51 of the 77 manifest
entries are already `"live"` — the kid (`eeri_v5.glb`, a Meshy-rigged,
14-clip skinned character), the excavator, both shipped worlds' full layer
sets (groundworks + pipeworks, sky through fore), UI art, textures. None of
it is wired into a scene yet; `asset_registry.gd` only proves the seam
parses and the files are really there.

## 3. A trap found on the very first import — read this before touching 3D

**`excavator_v1.glb`, `flag_v1.glb`, `flag_big_v1.glb` and `token_bolt_v1.glb`
fail to import into Godot 4.7.2's built-in glTF loader**, with:

```
ERROR: glTF: Can't import file '…', required extension 'KHR_mesh_quantization'
is not supported. Are you missing a GLTFDocumentExtension plugin?
```

These four are exported with quantized mesh attributes (smaller file size,
common from some Meshy/Blender export paths) and Godot's stock importer has
no extension registered for it. Everything else imported clean on the first
pass, including the skinned/rigged `eeri_v5.glb` and every 2D layer.

Two of these are **not decorative** — the excavator is the first ride
machine and `flag`/`flagBig` are the level-end object DESIGN.md §4.2
describes. Do not spend time re-authoring gameplay around a missing
excavator before checking whether this is fixed. Options, cheapest first:
1. Re-export the four from the source tool without mesh quantization (check
   `art-src/machines/` for the excavator's source; ART_PIPELINE.md names the
   export path).
2. Write or vendor a `GLTFDocumentExtension` that decodes
   `KHR_mesh_quantization` (per CLAUDE.md's "no new dependencies" rule this
   would need to be small and reviewed, not an addon pulled in wholesale).
3. Route these specific pieces through Blender/`gltf-transform` to strip
   quantization losslessly before they reach `assets/3d/`.

**Do not silently re-export at lower quality to work around this** — the
manifest's registered files are canon; if fixing the export changes the
`.glb` bytes, that goes through the normal `assets/` seam (bump `v`, keep the
node/clip contract, re-run the browser build's `eeri/test/smoke.cjs` too, so
the two builds stay reading the same file).

## 4. Port boundary

Port what DESIGN.md §1–§4 actually specifies, not a reimagining:

- on foot: run, jump, **stomp** (bounce a small enemy, gain height), **climb**
  (ladders/scaffold), read the site's hazards — this is 80% of playtime and
  has to stand on its own with every ride deleted (§1);
- machine rides: board at a marked point only, 30–40s of authored driving no
  amount of jumping could substitute for, step off (§1, §2);
- the reach budget rooms are proved against: run-jump apex 2.65 tiles,
  4.85 tiles across, **no pixel-precision jumps**, telegraphs ≥1.0s (§4);
- the midway checkpoint, infinite retries, no lives, no health bar —
  knockback + mercy frames is the entire damage model (§4.1);
- **`test/rooms.mjs`'s standing rule**: a ride-ending hazard may never stand
  between a machine and the job it is driving toward (§3) — if this port
  gets its own room prover, keep this invariant in it;
- level addressing, `EERI W-L` (§4, "Every level has an address");
- fi / en / ja, English as the per-key fallback (§4.4), same house rule the
  browser build and Piritori's port both follow;
- the collectible tiers: bolts x/100, three hidden golden bolts per level,
  one blueprint per world unlocking concept art (§4.2).

Do not build a world map (§4.1: "No map. Levels run 1 → 12 in order"), a
health/lives system, pixel-precision platforming, or original enemies
outside DESIGN.md §3's roster (hopper, roller, bucket) plus PHASING.md §2's
approved worker-bot family.

**Correction to an assumption this handoff first shipped with**: DESIGN.md
§4.1's "Three levels now" note is dated 2026-08-13 and is stale against the
actual v15.37 code. `node test/playthrough.cjs` (run against this repo,
2026-08-24) finishes **all twelve**, three per world, and the manifest ships
all four worlds' full layer sets (`groundworks`, `pipeworks`, `grove`,
`nightshift` — the last two are DESIGN.md §4.2's "Forest clearing and digs"
and "Evening site, under lights" under different working names):

| World | Levels (as titled in-game) |
|---|---|
| 1 — Groundworks | GROUNDWORKS · THE SCAFFOLD · THE HIGH WALL |
| 2 — Pipes and water hazards | THE WET TRENCH · THE PIPE RUN · THE PUMPHOUSE |
| 3 — Forest clearing and digs | THE CUT BANK · THE TIMBER LIFT · ROOT WORKS |
| 4 — Evening site, under lights | THE NIGHT SHIFT · THE LIT SCAFFOLD · LAST LIGHTS |

**Do not trust DESIGN.md's level counts over a gate run against real code** —
this is exactly the trap PHASING.md §0 exists to name for the design docs in
general ("newer owner direction... supersedes"), and it applies to a stale
progress note the same way it applies to a stale look call. If a future
session finds another such mismatch, re-run the gate and correct the doc
rather than trusting whichever one was faster to read.

## 5. Canonical data inputs

| Source | Godot responsibility |
|---|---|
| `assets/manifest.json` | every model/piece/layer/UI asset id, file path, status, node or clip contract |
| `assets/README.md` | how to read the table above — GLB axis/scale/pivot conventions, the two rig kinds (hand-cut nodes vs Meshy `"rig": "skinned"` clips), the layer rect/PPU table |
| `js/rooms.js` + `js/parts.js` (browser source, not yet ported) | all twelve built levels' actual tile layout and the room compiler — there is no separate JSON level format today; a Godot level importer has to either read this JS as data or a new authored format has to be designed and the browser build kept in sync, which is a Design/Level-lane decision, not an Engine one |
| `js/lang.js` (browser source) | the fi/en/ja strings — do not re-translate; port the same strings so the two builds don't drift into two different games in Finnish |

Unlike Piritori, Eeri's level data is **code, not JSON** — `rooms.js` is a
room *compiler*, and `PHASING.md`'s lane table gives it to Design/Level, not
Art or Engine. Decide with the owner whether the Godot port reads this
directly (e.g. a small JS-to-Godot-Resource converter script) or whether a
data format gets authored — do not silently duplicate three levels' worth of
hand-tuned platforming numbers into a second, divergent source.

## 6. Recommended structure, once gameplay starts

Mirrors Piritori's, adjusted for a platformer rather than a strategy sim:

```text
godot/
  autoload/
    asset_registry.gd   (exists)
    game_state.gd       (exists, empty — current world/level/checkpoint)
    loc.gd              fi/en/ja, ported from js/lang.js — NOT YET BUILT
  scenes/
    main.tscn           (exists — currently just the status placeholder)
    kid.tscn/.gd         run/jump/stomp/climb — the 80%
    level.tscn/.gd       tile collision, ladders, camera band
    ride_excavator.tscn  boom/stick/bucket control, seat/step/beacon contract
    hud.tscn             bolts, level address, pause
  tests/
    test_boot.tscn       (exists)
    test_rooms.tscn       geometry vs. the reach budget — mirrors eeri/test/rooms.mjs
    test_playthrough.tscn a bot finishes every level — mirrors eeri/test/playthrough.cjs
```

`GameState` should own current world/level/checkpoint and nothing else keeps
a second copy — the exact rule Piritori's `GameState` follows, for the exact
reason: two places holding "which level am I on" is how they disagree.

## 7. Art import rules

From `assets/README.md` — do not relearn these by trial and error:

- **3D**: glTF 2.0 single-file GLB, 1 unit = 1 tile, origin at ground/foot
  contact, **+Y up, facing +x**, flat normals, vertex colours or one shared
  palette-strip texture, no PBR channels, transforms applied.
- **Two rig kinds behind the same `getModel` call**: a hand-cut model
  declares rigid `nodes` the game rotates directly (e.g. excavator's `house`
  / `boom` / `stick` / `bucket` / `seat` / `step` / `wheels` / `beacon`); a
  Meshy auto-rig is a **skinned** mesh (`"rig": "skinned"`) declaring named
  `clips` instead, and carries `"height"` in tiles because Meshy rigs to
  real-world metres and the seam rescales on load. `eeri_v5.glb` is this
  kind — 14 clips including idle/walk/run/jump/climb/stomp/hurt.
  A Godot importer needs to branch on `rig == "skinned"` the same way
  `js/assets.js` does; treating a skinned character as a rigid-node model (or
  vice versa) will silently do nothing or throw.
- **2D layers**: WEBP with alpha (PNG still read by the size gate but WEBP is
  ~1/10th the size at the same quality), flat-colour cutout shapes with
  shading painted in, depth tint baked into the painting per lane
  (`LAYER_TINT`). The layer rect/px-per-unit table in `assets/README.md` is
  checked by the browser build's smoke gate against `js/layers.js` — a Godot
  importer should check the same table against whatever it derives, or a
  live layer can silently stretch off its authored scale.
- **Pieces carry all their states in one file** as sibling nodes `state0`/
  `state1`/`state2`… sharing one origin, plus a `grip` node if the piece is
  carried. Show exactly one state at a time; do not ship three separate
  files.

## 8. UI and accessibility rules

- **No key caps, no mouse icons, ever** (DESIGN.md §6.4, PHASING.md §4:
  "controller-first, mobile-friendly; no mouse/keyboard language anywhere").
  `js/glyphs.js` draws the browser build's button faces as inline SVG for
  exactly this reason — a Godot equivalent needs its own drawn glyph set for
  the same reasons, not an imported icon font with a keyboard key on it.
- Minimum interactive target 44 logical pixels (house convention across this
  whole family of projects).
- Landscape and portrait both have to work — the browser build already
  reflows; do not regress to a single fixed aspect.
- fi / en / ja, English as the per-key fallback (§4.4) — port `js/lang.js`'s
  actual strings rather than re-authoring them; a second translation
  diverging from the first is the exact trap `toko/`'s and Piritori's own
  fi/ja packs both record.

## 9. Save, determinism and accessibility

**The browser build has no mid-run save today** (DESIGN.md is silent on it —
"infinite retries," a checkpoint mid-level, and level-select for unlocked
levels is the entire persistence story). Do not invent a save format ahead
of the owner; if a Godot build needs one (e.g. to remember which levels are
unlocked across sessions), that is a design question to raise, not an
engine decision to make unilaterally.

Reduced-motion is not yet a concept in the browser build either (unlike
`gameoflife/` and `kindling/`, which both gate on `prefers-reduced-motion`).
Worth asking the owner whether Eeri needs it before assuming either way.

## 10. First Godot acceptance gate

The port is ready for review when a clean checkout can:

1. open on World 1, Level 1 (`EERI 1-1`) and control Eeri: run, jump, stomp
   a hopper, climb a ladder;
2. board the excavator at its marked point, drive an authored dig sequence,
   step off — and losing the ride mid-sequence drops the player back on foot
   rather than failing the level (the Yoshi rule, DESIGN.md §3);
3. finish a level and see its three-phase flag build (all twelve exist; a
   Godot port does not have to catch up to all twelve to pass this gate —
   proving the pattern on one world is the bar, same as browser-build
   Phase A did);
4. collect bolts (x/100 display), find at least one golden bolt, and see the
   HUD show the level's `W-L` address;
5. die (fall in a pit / take a hit with no mercy frames left) and resume at
   the midway checkpoint, not the level start;
6. reflow at phone portrait, phone landscape and desktop without a fixed
   aspect box;
7. play in all three languages with no visible English fallback where a
   translated string exists.

Before publishing, the existing browser-build gates must still pass — they
are the comparison source until a Godot gate independently proves the same
things:

```sh
node eeri/test/rooms.mjs
node eeri/test/fx-smoke.mjs
node eeri/test/dev-menu.mjs
NODE_PATH=$(npm root -g) node eeri/test/smoke.cjs
NODE_PATH=$(npm root -g) node eeri/test/playthrough.cjs
```

(Paths above are as they were inside Suds-Jack; this repo currently carries
only the Godot-relevant subset — see `godot/tests/`. The browser build
itself, `index.html` + `js/`, still lives in this repo too and is unchanged;
it is the comparison source, not dead code to delete.)

Add Godot headless boot/room/playthrough gates alongside these as they're
built; do not delete or stop running the browser gates while the two
implementations coexist — same rule Piritori's handoff states and for the
same reason: only one of them is validated against a real six-year-old
today, and it isn't the new one.

## 11. Git coordination

- This repo's history was extracted from Suds-Jack with `git-filter-repo` on
  2026-08-23 (same method, same day pattern as `mbace1/piritori-eden`
  2026-08-21) — `eeri/` flattened to the repo root, full commit history
  intact, all other branches dropped (they were Suds-Jack-wide agent
  branches, mostly already merged into what is now this repo's `main`).
- **`main` here is the only place to author.** The old monorepo's Eeri
  section recorded three separate accidental-fork incidents from editing
  `gh-pages` directly or branching off the wrong ancestor — the fix each
  time was the same: branch off `origin/main`, check `git merge-base`
  first, and if it returns nothing you are starting a fourth lineage.
- Fetch `origin/main` before every session. No rebase, no force push, no
  amend of pushed commits.
- Keep `.godot/`, `godot/data/` and any build output out of Git — see
  `.gitignore`.
- **Deploying still lands on Suds-Jack's `gh-pages`**, not this repo — the
  split changes nothing about where the game is played. The browser build
  copies to `Suds-Jack/eeri/` as before; a Godot web export would land in a
  new sibling folder there (e.g. `eeri-godot/`, mirroring `piritori-godot/`)
  and get linked from `hub/games.js` as its own cabinet or as a mode switch
  on the existing one — decide which with the owner before wiring it, since
  the existing `eeri` cabinet entry already points at the live browser game
  and two entries for one game is a hub decision, not an engine one.
- Version numbers are **decimal from v15** in the old monorepo
  (`vMAJOR.MINOR`) specifically because two lineages both claiming whole
  integers is what caused the forks above. If this repo keeps a `VERSIONS.md`
  log of its own going forward, keep that convention rather than resetting
  to v1 — or state clearly that it's a fresh count and why.
